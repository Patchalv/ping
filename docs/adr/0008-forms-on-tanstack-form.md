# Web forms are built with TanStack Form and the shared zod schemas

**Status:** accepted

The first two forms (Create channel and sign-in) had no library. They used uncontrolled inputs, read the values with `FormData`, and checked them with `safeParse`. Each field repeated the same `data-invalid`, `aria-invalid`, `aria-describedby` and `FieldError` wiring by hand. That held for two small forms. The Threads slice (#38) brings much heavier ones: a new Thread with a TipTap description and Attachments, the Thread Response composer, and an unsent draft kept in the browser. Admin screens, password flows and Channel settings come after. #67 settled the approach before #38 copies it.

## Decision

- **TanStack Form 1.x (`@tanstack/react-form`).** Each form calls `useAppForm` from `apps/web/src/components/form.tsx`. It builds from the bound pieces there: `form.Form`, `field.TextField`, `field.TextareaField`, `field.RadioGroupField` and `form.SubmitButton`. A custom control (the TipTap editor) uses `useFieldWiring()` to get the same wiring. Every field gets its label, `aria-invalid`, and its error tied to the control by `aria-describedby`, without repeating them per form.
- **The zod schemas in `packages/shared` are the validators, passed in directly.** zod 4 implements Standard Schema, and TanStack Form accepts a Standard Schema as a validator: `validators: { onDynamic: createChannelBody }`. No resolver package and no copy. The schema's own messages are what the Staff member reads. Sign-in gained `signInBody` for the same reason. The form holds the schema's input, not its output, so `onSubmit` sends `schema.parse(value)` to get the trimmed, defaulted body. It never repeats a transform by hand.
- **When it validates:** on submit first, then again on every change once a submit has failed (`validationLogic: revalidateLogic()`). Nothing complains while the Staff member is still typing. Once a submit has failed, each mistake clears as it is fixed.
- **Focus:** `form.Form` submits through TanStack Form, then moves focus to the first field with an error, in page order. This applies whether the schema or the server found the error. Controls carry `data-field` and an id from `controlId(formId, name)`. A radio group's focus goes to its radio. A TipTap editor's contenteditable takes the id and focus itself.
- **Server issues:** when a mutation fails, the form's `onSubmit` catches the `ApiError`. `showServerIssues(formApi, error.issues)` puts each issue on its field, as the field's `onServer` error. Changing that field drops the issue. Until then, submitting again only refocuses the field, because the server would refuse the same value again. If any issue has no field to land on, the error's message also shows as a form-level failure. A failure no field explains ("Can't reach Ping. Try again.", a refusal) is kept in local state and shown with `FormError`. It is never put in the form's own error map, because a form-level error there would block the retry.
- **Pending:** `form.SubmitButton` is disabled, with its pending label, only while the form is submitting. The form's `onSubmit` awaits the mutation (`mutateAsync`). The button is never disabled for being invalid, because pressing it is how the Staff member finds out what is missing.
- **Controlled editors join as fields.** The TipTap description is a field whose value is the ProseMirror JSON (ADR 0003). The editor's `onUpdate` calls `change(editor.getJSON())`. The editor element gets the field's id, `aria-invalid` and `aria-describedby` through `editorProps.attributes`. `useEditor` re-applies these on each render, so the error state follows. A restored draft reaches the editor as its initial `content`. A value the form changes later (emptying it after sending) is pushed into the editor from that same handler, with `editor.commands.clearContent()` or `setContent()`. It is never synced during render or in an effect. The spike synced during render, and #38 must not copy that.
- **Attachments are not proven yet.** The plan is a field holding the uploaded Attachment ids, with the upload run from the field's own handlers. While an upload is unfinished, sending must wait. `form.SubmitButton` reads only `isSubmitting` today, so #38 adds that state, for example as a field-level async validator, which makes the form `isValidating`.
- **Drafts without an effect.** The draft is read once, lazily, as the form's `defaultValues` (`useState(() => readDraft(key))`). It is saved from TanStack Form's form-level `listeners.onChange`, debounced, which is an event and not an effect. The listener skips while the form is submitting. It is removed when the form is sent, and also whenever the form is empty again. A debounced write that lands after sending finds an empty form and removes the draft instead of bringing it back. After sending, the empty values become the new defaults. Otherwise `useAppForm` would reset the form back to the restored draft.
- **Drafts are per Staff member.** Each key is `ping:draft:<staffMemberId>:…`, so the next person to sign in on the same browser never sees someone else's draft. This is the same rule as one QueryClient per Staff member (ADR 0006). Signing out clears that Staff member's drafts. #38 builds this.
- **Form state in React context is allowed.** `createFormHook` passes the form and field to the bound components through context. Like `SidebarProvider` (ADR 0007), this is UI state for one form, never server data, so it is an allowed exception to ADR 0006.

### What the spike showed

A throwaway branch (`67-forms-spike`, not merged) built a new-Thread form with a title and a TipTap description on `components/form.tsx`. It was checked in the browser. On an empty description, the submit focused the editor, set `aria-invalid` on it and tied it to "Write a description." Typing cleared the error. The draft came back after a reload. Sending within the debounce window left no draft behind. The first try reset the form to the restored draft after sending, which is why the empty values have to become the new defaults.

## Consequences

- It costs one dependency, `@tanstack/react-form`. It brings `@tanstack/form-core`, `@tanstack/store`, `@tanstack/react-store`, `@tanstack/pacer-lite`, `@standard-schema/utils` and `@tanstack/devtools-event-client`. That last one is an event bus for TanStack's devtools and stays idle without them. The built SPA grew by 16 KB gzipped (249.7 KB to 265.7 KB). `pnpm audit` reports nothing.
- Forms are controlled, so every keystroke re-renders the field being typed in, but not the rest of the form.
- There are no React component tests, so the pure parts (`lib/form-issues.ts`) have unit tests. Playwright covers the behaviour: a schema mistake and a server mistake each land on their field and take focus, both clear when fixed, and an offline failure, in Create channel or sign-in, says so and can be retried. A server issue's `path` must match a field name exactly (the server joins zod's path with dots), which array fields such as Attachments must keep to.
- A new kind of control (date, select, Mention picker) gets a bound field in `components/form.tsx` before a form uses it, so the wiring stays in one place.

## Considered options

- **Native forms and zod, with a helper for the field wiring:** rejected. Every form would still hand-roll validation timing, focus, a controlled TipTap value, pending state and drafts. That is most of what #38 needs.
- **React Hook Form with `zodResolver`:** not chosen. It's the most widely used, it focuses the first invalid field by default, and it's about 14 KB gzipped with the resolver. But it needs `@hookform/resolvers` to read the zod schemas. Its change subscription (`watch` or `subscribe`) is normally set up in an effect, which the effect rule forbids, so drafts would need an exception. It also sits outside the TanStack stack the app already uses (ADR 0006).
- **Base UI's own `Form` and `Field`:** rejected. They add nothing to the bundle, focus the first invalid field and accept server errors. But validation is per field, not one schema for the whole form. Base UI keeps no form values or dirty state, so a TipTap value needs a hidden input and drafts need hand-rolled state.
